## 목표와 현재 단계

동의한 참여자가 광고·예고편·영상 콘텐츠를 시청할 때 나타나는 반응을 구간별로 정리하고, 사용자의 장면별 질문에 분석 근거와 함께 답한다. 콘텐츠 제작자와 마케팅 담당자가 반응 변화 구간을 찾아 편집·후속 테스트에 활용하는 것이 목표다.

현재는 **비용 없는 사전검증을 마친 단계**다. 기존 오프라인 자가진단 3종, 원본 구간 집계의 24개 동작 검사, 실제 얼굴 감정 모델의 합성 이미지 CPU 추론을 수행했다. 공식 Marketplace·호스팅·Cloud Run 요건도 확인했다. 실제 참여자 영상의 정확도·성능, STT 전체 연결, GE/GCP 배포와 실제 비용은 미검증이다. 원본 자료의 시연·방송 활용 이력과 법적 적합성은 별도 확인이 필요하다. 자세한 증빙과 제약은 검증 문서에 기록했다.

우선 콘텐츠 반응 분석 한 가지에 집중한다. **EmoAI가 구조화 분석 결과와 Gemini 기반 해석·질의응답을 제공하고, GE는 A2A를 통해 사용하는 창구가 되는 구조**를 출시 후보로 둔다. 기존 OpenAI 해석 단계의 대체는 별도 시험한다. GE가 영상만 보고 EmoAI 측정값을 만들어 내는 방식은 사용하지 않는다.

## 기존 EmoAI 구현 확인

확인일: 2026-10-23. 사용자 설명과 `C:\ableai\XR_workspace\Meta Glass\exhibition`의 문서·C++ 소스를 확인하고 제한된 오프라인 시험을 수행했다. 모델 정확도 시험은 수행하지 않았다. 아래는 해당 전시 버전의 구성으로, 다른 EmoAI 배포 버전 전체를 뜻하지 않는다.

| 단계 | 확인한 구성 | 근거 파일 |
| --- | --- | --- |
| 얼굴 추적·AU | OpenFace 기반 68점 랜드마크, 얼굴 자세·시선, 17개 AU 채널 | `src/face_pipeline.cpp`, 전시 화면 설명 |
| 얼굴 감정 분류 | 얼굴 이미지를 별도 신경망에 입력해 감정 점수 산출. 확인한 분류 코드는 TFLite 로딩 경로 사용 | `src/emotion_classifier.cpp` |
| 개인 보정·융합 | 무표정 기준선과 표정·음성·언어 채널을 사용. 음성은 각성도에 반영하고 긍정·부정 판단에는 사용하지 않는 설계 | 전시 화면 설명, `src/emotion_fusion.cpp` |
| 음성 특징 | 피치·음량·발화속도 추정 및 개인 기준 대비 편차. 별도 딥러닝 모델이 아닌 신호 계산 모듈 | `src/voice_frontend.h` |
| STT | 별도 STT 서버에 PCM을 WebSocket으로 보내 전사 이벤트 수신 | `src/stt_client.h` |
| 언어 분석 | 확정 전사문에서 한국어 감정 어휘를 찾아 유인가·각성도와 근거 단어 산출 | `src/text_affect.h` |
| 구간 집계 | 감정 분포·AU 평균/최대·시선·집중/흥미/몰입/긴장 요약·발화·미검출 구간을 JSON으로 생성 | `src/analysis_session.cpp` |
| 최종 AI 해석 | 구간 요약 JSON을 OpenAI Chat Completions에 보내 한국어 설명 생성. 헤더의 기본 모델은 `gpt-4o-mini`이며 실제 실행 설정은 별도 확인 | `src/llm_client.h`, `src/llm_client.cpp` |

따라서 EmoAI는 단일 로컬 모델만으로 설명하기보다 **로컬 분석 모듈 + STT 연동 + 채널 융합·구간 집계 + LLM 해석**으로 구성된 멀티모달 시스템으로 정의한다. 68점 좌표만으로 모든 감정 판단을 하는 단일 모델 구조로 표현하지 않는다. README의 HSEmotion 설명과 실제 분류 코드의 모델 로딩 경로가 달라, 배포 모델 파일·버전·라벨 수는 실행 설정과 함께 확정해야 한다.

### 기존 API와 재사용 범위

`src/main.cpp`에는 이미 로컬 HTTP API가 있다.

- `POST /api/source/mode`, `POST /api/source/frame`: 파일 모드 전환과 JPEG 프레임 입력.
- `GET /api/data`, `GET /api/events`: 현재 분석 결과 JSON과 SSE 스트림.
- `POST /api/analysis/start`, `POST /api/analysis/result`: 구간 수집 시작 및 기존 LLM 해석 요청.
- `POST /api/calib/start`: 개인 무표정 보정 시작.

파일 입력은 브라우저가 영상을 재생하며 JPEG 프레임을 전달하는 구조다. 확인한 경로에는 파일 오디오의 STT 전달과 원본 콘텐츠 타임코드 전송이 없다. 영상·음성을 함께 처리하는 배치 입력과 시간 정렬을 별도로 구현해야 한다.

현재 `/api/analysis/result`는 구간을 마감하고 다음 세션을 시작하며 LLM 호출까지 수행한다. 저장된 결과를 단순 조회하는 API와 구분해야 한다. 확인한 응답은 해석 문자열과 메타데이터 중심이며, GE에 근거를 전달하려면 내부의 구간 요약 JSON을 반환·보관하는 경로를 마련하는 것이 우선이다.

GE 연결은 기존 분석 모듈과 JSON 집계를 재사용하고, 작업·결과 관리 API와 연결 계층을 보완하는 방향으로 검토한다. Marketplace용 제품은 자체적으로 분석·해석·질의응답을 수행하고 GE는 대화 창구로 사용하는 구성을 우선한다. 기존 OpenAI 해석 호출은 Gemini 기반 해석으로 전환하는 안을 검토하며, 구체 모델·등록 적합성·비용은 확인 후 결정한다. 기존 STT 서버의 배포 위치·사용 비용도 별도 확인한다.

## 사용자와 사용 시나리오

| 사용자 | 질문·업무 | 제공할 결과 |
| --- | --- | --- |
| 광고대행사·브랜드 담당자 | 광고의 어느 구간에서 반응이 변했는가? | 구간별 변화, 관측 근거, 재검토할 장면 |
| 방송·OTT·영상 제작자 | 예고편의 어떤 장면을 수정할 것인가? | 반응 상승·하락 구간과 편집 가설 |
| 콘텐츠 테스트 담당자 | A안과 B안 중 어느 쪽의 반응이 나은가? | 비교 조건과 지표별 차이, 해석 한계 |

질문 예시: “이 광고의 반응 변화 구간을 요약해줘”, “2분 30초 전후에 어떤 신호가 달라졌어?”, “A안과 B안의 엔딩 반응을 비교해줘.”

“왜 반응이 떨어졌어?”라는 질문에는 관측된 변화와 가능한 해석을 구분한다. 표정·음성 변화만으로 장면이 반응의 원인이라고 확정하지 않는다.

## 단계별 범위

| 단계 | 할 일 | 완료 시 결과 |
| --- | --- | --- |
| 1. 결과 기반 수동 POC | 기존 엔진의 비식별 분석 결과와 콘텐츠 구간 정보를 수동 입력 | 구간 요약·근거 설명의 정확성 확인 |
| 2. 녹화 영상 분석 연동 | 동의·권한을 확인한 녹화와 타임라인을 승인된 기존 엔진에 전달 | 분석 요청·상태 조회·결과 조회 흐름 확인 |
| 3. 시청 테스트 운영 | 테스트 링크, 동의, 웹캠 수집, 타임라인 동기화 | 참여부터 결과 생성까지의 전체 흐름 확인 |
| 4. 버전 비교·사업화 | 비교 조건을 갖춘 A/B 분석, 판매·배포 방식 검토 | 비교 보고서와 별도 사업화 계획 |

첫 POC는 테스트 1건·콘텐츠 1편의 결과 요약부터 시작한다. 엔진 출력 예제가 없으면 출력 스키마를 먼저 합의하고, 가상 데이터는 형식 검증용으로만 표시한다. 가상 데이터로 분석 성능을 평가하지 않는다.

고객 반응 분석, 학습 몰입도 분석, 뷰티 전후 AU 비교는 원본 제안서의 확장 후보로 남긴다. 데이터 수집·평가 목적·검증 방식이 달라 각각 별도 기획 후 판단한다. 초기 범위에는 의료 판단, 직원 감시, 채용 평가, 학생 개인 평가를 포함하지 않는다.

## 역할과 처리 흐름

초기에는 하나의 워크플로에서 역할을 분리한다. 여러 독립 에이전트나 A2A 배포를 첫 POC의 필수 조건으로 두지 않는다.

| 역할 | 책임 | 확인할 사항 |
| --- | --- | --- |
| GE 대화·요청 해석 | 테스트·콘텐츠·구간과 사용자 질문 식별 | 접근 권한, 모호한 시간·버전 확인 |
| 입력·품질 확인 | 동의 범위, 기준선, 시각 동기화, 신호 누락 확인 | 분석 가능·일부 가능·분석 불가 구분 |
| EmoAI 분석 엔진 | 지원되는 표정 AU·음성·발화 신호와 지표 산출 | 실제 지원 신호, 단위, 계산 방식, 버전 |
| 결과 해석·보고 | 구간별 집계, 변화 구간 설명, 비교와 개선 가설 작성 | 수치·시간·근거 일치, 과도한 해석 방지 |

흐름: 요청 및 권한 확인 → 입력 품질 확인 → 기존 결과 수신 또는 분석 요청 → 상태·결과 확인 → 집계·요약 → 구간별 질의응답.

시청 중 발화가 없으면 음성·발화 분석을 생략한다. 콘텐츠 자체의 배경음·등장인물 음성을 참여자의 반응으로 사용하지 않는다. 얼굴 미검출·녹화 누락은 낮은 몰입 점수가 아니라 결측으로 처리한다.

## 입력과 결과 데이터

2026-10-23 [[GE_Agents/07_EmoAI_Agent/02_분석결과_JSON_규격|분석 결과 JSON v1.0.0]]을 확정했다. 결과는 참여자 녹화 1건 단위로 제공하며 결측을 null·상태·사유로 표현하고, 최대 1초별 측정값·녹화/콘텐츠 시간 매핑·음성 출처와 STT 상태·시각이 있는 이벤트를 포함한다. 스키마와 교차 필드 검증을 함께 적용한다. 실제 엔진의 새 규격 출력은 다음 구현 대상이다.

| 구분 | 필요한 정보 |
| --- | --- |
| 테스트 | 테스트 ID, 콘텐츠 ID·버전·길이, 테스트 목적 |
| 참여·동의 | 가명 참여자 ID, 동의 확인 상태·허용 목적, 결과 접근 범위 |
| 콘텐츠 구간 | 시작·종료 시각, 장면 설명 또는 자막, 녹화와 콘텐츠의 시간 오프셋 |
| 분석 조건 | 개인별 무표정 기준선 확보 여부, 촬영·음성 품질, 유효 분석 구간 |
| 분석 결과 | 구간별 관측 신호·지표·단위, 지표 정의, 유효 참여자 수, 결측·품질 정보 |
| 추적 정보 | 분석 ID, 엔진·모델 버전, 실행 상태, 결과 생성 시각, 근거 참조 |

정서·집중도·흥미·몰입도는 원본 자료의 목표 지표다. 각 지표의 정의, 산출식, 점수 범위, 검증 근거와 실제 제공 여부를 확인하기 전에는 확정된 측정값으로 취급하지 않는다. AU 변화와 심리 상태에 대한 해석도 구분한다. 불확실성 수치가 제공되지 않으면 신뢰도를 임의의 퍼센트로 만들지 않는다.

## 기본 출력

1. **분석 개요:** 콘텐츠·버전·참여자 수, 유효 분석 범위, 기준선·신호 품질.
2. **구간별 반응:** 제공된 지표의 변화와 주요 상승·하락 구간. 그래프를 만들 경우 결측 구간을 표시한다.
3. **근거 설명:** 콘텐츠 시각, 실제 AU·음성·발화 근거, 해당 결과 참조.
4. **해석과 개선 가설:** 관측 사실과 추정 설명을 구분하고, 후속 편집·테스트 후보를 제시한다.
5. **한계와 확인 사항:** 표본·누락·동기화·기준선 문제와 해석할 수 없는 항목.

구간별 설명은 `00:25~00:30 / 관측 변화 / 근거 / 해석 / 한계` 형식으로 작성한다. 실제 데이터가 없으면 예시 수치를 채우지 않는다. 참여자가 적은 구간은 수를 함께 표시하고 집단 전체의 반응으로 일반화하지 않는다.

A/B 비교에서는 참여자 구성, 노출 순서, 길이·대응 장면, 유효 표본 수와 동일 지표 사용 여부를 확인한다. 조건이 다르면 차이를 서술하되 우열을 단정하지 않는다. “긍정 반응이 높음”과 광고 효과·구매 전환 향상도 구분한다.

## 구축 방식과 공통 제약

### 프로젝트별 GCP 허용과 예산

2026-10-23 사용자 결정: **이 프로젝트는 GCP 사용을 허용하며 월 예산 상한은 USD 70**이다. 공통 제약의 GCP 금지에 대한 프로젝트별 예외로 적용한다. GWS 사용 허용이나 다른 프로젝트의 비용 허용으로 확대하지 않는다.

예산은 우선 이 프로젝트의 GCP 실행·저장·네트워크·모델 호출·로그 등 합산 비용 기준으로 관리한다. 기존 GE 구독료와 회사 서버 비용은 별도 항목으로 표시한다. GCP 밖의 신규 유료 서비스가 필요하면 이 예산에 포함되는지 먼저 결정한다.

초기 운영 목표는 월 USD 50 이하로 두고 USD 20은 사용량 변동 여유로 남기는 안을 제안한다. 이는 내부 예산 배분안이며 실제 서비스 가격 견적이 아니다. 최대 영상 길이·월 작업 수·동시 실행 수를 제한하고, 작업별 처리시간·모델 사용량·저장량을 측정해 월 허용량을 정한다. 월 70달러로 운영 가능하다는 결론은 실제 비용 측정 전까지 유보한다.

공개 API·A2A 서비스, 임시 영상·결과 저장, Gemini 해석을 GCP 설계 후보에 포함한다. 분석 엔진은 기존 회사 서버를 활용하는 POC와 GCP로 옮기는 안의 비용·모델 배포 가능성을 비교한다. 회사 서버와 GCP를 나누는 구조의 Marketplace 호스팅 적합성은 별도 확인한다. 상시 GPU 운영은 초기 전제로 두지 않는다.

비용 관리에는 예산 알림과 함께 애플리케이션의 작업 접수 제한·동시 실행 제한·파일 보관 기한을 설계한다. 예산 알림만으로 지출이 자동 차단된다고 가정하지 않는다. 이번 결정은 기획·설계에 반영한 것이며 실제 GCP 리소스는 아직 생성하지 않았다.

### 회사 서버와 GCP 분석 비교

2026-10-23 비교 결론: **빠른 기능 검증은 기존 회사 서버를 활용하고, Marketplace 출시 목표 구조는 GCP에서 분석까지 수행하는 안을 우선한다.** 현재 엔진의 CPU 실행 경로는 있지만 Linux 컨테이너·파일 일괄 분석·STT 통합은 검증하지 않았다. 전시 빌드는 Windows 전용 캡처 소스를 포함하므로 실행 파일을 그대로 Cloud Run으로 옮기는 작업으로 보지 않는다.

| 기준 | 회사 서버 분석 + GCP 서비스 | GCP에서 분석까지 수행 |
| --- | --- | --- |
| 구성 | GCP의 A2A·인증·작업 관리·Gemini, 회사 서버의 EmoAI·STT | GCP의 A2A·인증·작업 관리·EmoAI·STT·Gemini |
| 코드 재사용 | 기존 Windows 환경을 활용하기 쉬움 | 분석 코어를 캡처·UI와 분리하고 Linux 배치 실행 검증 필요 |
| 비용 구조 | GCP 분석 비용은 줄지만 회사 장비·전력·운영 비용은 별도 | 분석 CPU·메모리·STT·저장·전송까지 GCP 예산에 반영 |
| 운영 | 회사 서버의 가동·회선·장애가 고객 서비스에 영향 | 회사 회선 의존은 줄지만 작업 실패·재시도·확장 관리 필요 |

| Marketplace | 핵심 분석이 사외 GCP에 없으므로 사전 적합성 확인 필요 | 제품을 주로 GCP에서 호스팅한다는 요건에 더 직접적으로 부합 |
| 월 USD 70 | 기존 서버 여유가 있다면 POC 예산 관리에 유리 | 짧은 영상·적은 작업·요청 시 CPU 실행으로 검증. 실측 전 보장 불가 |

Marketplace 요건에는 완전 GCP형과 하이브리드형이 있다. 하이브리드는 핵심 제품이 GCP에서 실행되고 고객 사용 증가 시 GCP 에이전트의 소비가 가장 빠르게 증가해야 한다. GCP에 연결 API만 두는 것으로 충족한다고 가정하지 않는다. GCP 전체 구성도 등록 승인을 보장하지 않는다. 이번 공식 문서 확인 결과와 링크는 검증 문서에 기록했다.

GCP 분석은 상시 VM과 필요 시 실행하는 컨테이너를 나누어 검토한다. 초기에는 CPU 기반 배치 컨테이너를 우선 후보로 두고, 장시간 작업은 Cloud Run Jobs 등 작업 실행 방식의 제한·단가를 확인한다. 모델 초기 로딩 시간도 처리 비용에 포함한다. STT 서버의 CPU/GPU·메모리 요구량이 아직 확인되지 않아 얼굴 분석 비용만으로 전체 견적을 내지 않는다.

예산 검토식은 `월 분석 작업 수 × 작업당 실측 CPU·메모리 실행비 + STT + Gemini + 저장·전송·로그·빌드 등`이다. 참여자 30명의 녹화는 콘텐츠 1편이더라도 분석량은 녹화 30건으로 계산한다. 상시 VM은 월 약 730시간의 실행비와 디스크·네트워크 등 부대비를 합산하며, 비상시 실행 방식은 실제 할당 자원과 실행시간을 기준으로 비교한다. 리전·운영체제·과금 방식이 정해지기 전 달러 단가를 확정하지 않는다.

다음 검증은 동일한 짧은 녹화로 회사 서버 처리시간·최대 메모리·STT 의존성을 측정하고, 분석 코어의 Linux 실행 가능성을 확인하는 것이다. 이후 GCP에서 동일 결과와 작업당 비용을 측정해 월 허용 녹화 수를 정한다. Linux 이식이 오래 걸리면 회사 서버로 기능 POC를 진행하되 Marketplace 출시 구조와 구분한다.

### 분석 API 연결

EmoAI의 로컬 분석 모듈은 회사 실행 환경에 두고, 기존 HTTP API와 구간 집계를 외부 연동에 맞게 정리하는 구조를 검토한다. 모델 가중치를 GE에 업로드하는 것을 전제로 하지 않는다. 로컬 API의 존재는 소스로 확인했으며, GE에서 접근 가능한 배포·인증·작업 격리는 아직 검증하지 않았다.

수동 결과 요약 POC에는 API가 필요하지 않다. GE에서 분석 요청부터 결과 조회까지 자동화하려면 호출 가능한 인터페이스가 필요하다. 우선 내부 분석 API를 정의하고, GE 연결 방식이 확인되면 MCP 도구 또는 A2A 인터페이스를 연결 계층으로 검토한다. 일반 REST API를 만들었다고 GE가 바로 호출할 수 있는 것은 아니다.

출시 후보 흐름: `GE → A2A 서비스 → 작업 관리 → GCP 배치 EmoAI 분석 → 구조화 결과 저장 → Gemini 해석·질의응답 → GE`. 회사 서버 분석은 초기 기능 POC 및 하이브리드 적합성 검토용 후보로 둔다.

최소 API 기능 후보는 분석 요청, 처리 상태 조회, 결과 조회다. 시간이 오래 걸리는 분석은 작업 ID를 반환하고 이후 결과를 조회하는 방식으로 설계한다. 원본 영상의 전달 경로와 GE에 반환할 결과 범위는 별도로 결정한다. 결과 설명만 필요하면 원본 영상은 회사 환경에서 처리하고 집계 결과만 전달하는 구성이 가능하다.

로컬 PC의 localhost나 사내 전용 주소를 클라우드 GE에서 바로 호출할 수 있다고 가정하지 않는다. 지원되는 네트워크·인증·계정별 연결 설정을 확인해야 한다. 회사 서버에서 모델을 실행하는 것과 GE 연결 설정에 GCP 리소스가 필요한지는 별개이므로, 공통 제약 충족 여부도 따로 판단한다.

첫 POC는 분석 결과를 수동으로 제공하고 GE가 요약·질의응답을 수행하는 경로를 우선 검토한다. 파일 업로드·대화 입력의 실제 지원 형식, 용량과 조직 정책은 현재 계정에서 확인한다. 이 폴더에 저장했다고 GE가 자동으로 읽거나 검색하는 것은 아니다.

엔진 연동은 기존 실행 환경·API 재사용과 월 USD 70 예산 내 GCP 구성을 함께 검토한다. 분석 ID를 이용해 요청·처리 중·완료·실패를 구분하고, 재시도 때 중복 분석과 중복 과금이 발생하지 않도록 설계한다. 지원되지 않는 도구 호출을 완료한 것처럼 보고하지 않는다.

원본 제안서는 Google Cloud 운영, Marketplace 판매, A2A, OAuth·Dynamic Client Registration, 결제 연동과 설치형 패키지를 제안한다. **GCP 허용에 따라 Marketplace 등록을 목표 경로로 포함한다.** 먼저 녹화 영상 분석·시간별 JSON·근거 기반 보고서와 후속 질문 흐름을 완성한다. A2A와 Agent Card는 기존 초안을 검토해 실제 구현 범위에 맞게 수정하며, 지원 버전·인증·판매자 등록·심사 요구사항은 별도 확인한다.

Agent Card의 `example-ableai.com` 도메인, 스트리밍·푸시 알림 선언, 테스트 생성·분석·비교 기능은 실제 구현 증빙이 아니다. 가격 가설, 경쟁사 가격, 방송 레퍼런스, 판매·등록 요건도 검증 전 외부 확정 문구로 사용하지 않는다. 사업화 검토는 현재 GE 내부 POC와 별도 과제로 관리한다.

## 데이터 취급과 사용 원칙

- 목적과 수집·분석 범위에 동의한 참여자 자료만 사용한다. 동의 상태를 확인할 수 없으면 분석을 진행하지 않는다.
- 결과 요약 POC는 비식별 결과를 우선 사용한다. 원본 녹화·개인 식별 정보의 GE 전송은 필수 조건으로 두지 않는다.
- 테스트·고객별 접근 권한을 분리하고, 일반 보고서는 집계를 기본으로 한다. 개인별 결과의 필요성과 접근 범위는 별도 결정한다.
- 원본 삭제는 목표 정책이다. 삭제 시점, 실패 시 보관 기한, 임시 파일·백업·로그의 처리와 확인 기록을 정한 뒤 실제 삭제 여부를 검증한다. 파생 결과의 보관·삭제 기한도 별도로 정한다.
- 분석은 콘텐츠 개선을 위한 참고자료로 제공하며 건강·정신 상태 진단이나 개인의 능력·성향 판정에 사용하지 않는다.

원본 제안서의 법률·규제 관련 서술은 이번 기획의 적합성 근거로 채택하지 않는다. 비의료 표시, 고객만 분석하는 구성, 집계 출력만으로 모든 사용 환경의 적합성이 확보된다고 전제하지 않고, 확장 시 적용 지역과 실제 용도를 별도로 검토한다.
