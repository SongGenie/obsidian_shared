# EmoAI Agent 비용 없는 사전 검증

기획: [[GE_Agents/07_EmoAI_Agent/00_기획]]  
기존 입출력: [[GE_Agents/07_EmoAI_Agent/자료/기존_LLM_입출력_분석]]
후속 결과 규격: [[GE_Agents/07_EmoAI_Agent/02_분석결과_JSON_규격]] (규격·계약 시험 완료, 엔진 적용 미구현)

## 결론

**기존 분석 코어와 구간 집계를 재사용해 제품화를 진행할 근거는 있다. 현재 전시 프로그램을 그대로 Marketplace에 배포할 수 있는 상태는 아니다.** 오프라인 자가진단 3종, 원본 구간 집계 코드의 24개 동작 확인, 얼굴 감정 모델의 로컬 CPU 추론을 수행했다. 특히 결측 처리·파일 음성 입력·시간 정렬·고객별 작업 격리를 먼저 보완해야 한다.

이번 범위는 비용을 발생시키지 않는 사전 검증이다. GCP 리소스 생성·Cloud Build·배포·유료 모델 호출·STT 서버 연결은 하지 않았다. 실제 참여자 영상도 사용하지 않았다. 현재 회사 서버의 전시 프로젝트는 수정하지 않고 읽기 및 명시적 오프라인 진단 실행만 했다. 검증 코드·빌드 산출물은 Obsidian의 이 프로젝트 하위에 만들었다.

이 문서의 사전검증 완료는 Marketplace 출시 준비 완료나 모델 정확도 검증 완료를 뜻하지 않는다.

기존 EXE는 2026-09-28 빌드 파일이며 현재 소스와의 완전한 일치까지 입증하지 않았다. 별도 집계 시험은 현재 소스 파일을 복사해 새로 컴파일했다. 얼굴·감정 결과 자료형만 원본 선언에서 추출해 무거운 OpenCV/OpenFace 헤더 의존성을 제거했으며, 집계 구현은 변경하지 않았다. 검출·추론 코드는 이 집계 시험에 포함되지 않는다.

감정 모델 시험은 `emotions_mobilenet.tflite`와 7행 라벨 파일을 확인했다. 현재 `main.cpp`의 기본 로딩 경로도 이 파일이다. 다른 `.ptl` 파일이 폴더에 존재하는 것만으로 HSEmotion 모델이 실행된다고 볼 수 없다. 실제 실행 인자의 `--models` 경로는 별도 확인해야 한다. 합성 입력 1회의 로딩 0.0744초·추론 0.0423초는 현재 PC와 별도 Python OpenCV 환경에서 얻은 값이며 영상 전체의 FPS·메모리·GCP 성능 추정에는 사용하지 않는다.

## 직접 재현한 구간 집계

합성 지표를 3개의 1초 버킷에 넣고 추가로 검출됐지만 신뢰되지 않는 프레임 1개, 미검출 프레임 1개를 넣었다.

| 항목 | 예상 | 실제 |
| --- | --- | --- |
| 총 프레임 | 5 | 5 |
| 검출률 | 4 / 5 | 0.80 |
| 신뢰 프레임 비율 | 3 / 검출 4 | 0.75 |
| 집중 평균 | (20 + 60 + 100) / 3 | 60, moderate |
| 집중 추세 | 앞 1버킷 평균 20 → 뒤 2버킷 평균 80 | rising, delta 60 |
| AU06 평균·피크 | 평균 2, 피크 3 | 2, 3 |
| 대표 감정 비율 | Neutral 2버킷, Happiness 1버킷 | 0.67, 0.33 |
| 감정 타임라인 | 변화점만 2개 | 0초 Neutral, 2초 Happiness |
| guidance | 로그용에는 존재, LLM 전송본에서는 제거 | 동일하게 확인 |

[합성 입력으로 생성한 실제 집계 JSON](자료/검증/synthetic_session_summary.json)을 보관했다. 형식 설명을 위해 임의로 작성한 JSON이 아니라 원본 집계 함수를 실행한 출력이지만, 입력은 가상 지표이므로 실제 사람의 분석 결과로 사용하면 안 된다.

## 기획에 영향을 주는 발견

### 결측값이 낮은 점수로 보이는 문제

얼굴은 검출되지만 신뢰 가능한 프레임이 0인 입력에서 `prompt_state.confidence`는 `insufficient`로 나오면서도 `attention_summary.mean=0`, `level=low`가 생성된다. [재현 JSON](자료/검증/unreliable_only_summary.json).

현재 분석 결과 API의 LLM 호출 차단 기준은 얼굴 검출률 0.40 미만이다. 검출은 잘되지만 신뢰 프레임이 없는 경우는 이 기준만으로 차단되지 않는다. 새 API에서는 `valid_samples`, `valid_duration_sec`, `status`를 제공하고 유효 자료가 없으면 `mean=null`, `level=unavailable`로 표시해야 한다. LLM에도 품질 게이트를 동일하게 적용한다.

### 파일 분석은 영상과 음성의 완전한 배치 분석이 아님

`web/js/app.js`는 파일 영상을 캔버스에 그려 JPEG만 `/api/source/frame`에 전송한다. 영상의 소리는 브라우저에서 재생하며 파일 오디오를 PCM으로 추출해 STT에 보내는 경로는 확인되지 않았다. `main.cpp`의 음성 경로는 마이크 캡처 중심이다. 파일 분석과 마이크가 함께 켜지면 분석 영상과 다른 음성을 섞을 위험이 있어 입력 소스를 명시적으로 분리해야 한다.

수정 요구: 영상 컨테이너에서 프레임과 오디오를 같은 시간 기준으로 추출하고, 참여자 음성과 콘텐츠 배경음을 구분한다. 원본 광고 영상만 올려서는 시청자의 반응을 알 수 없으며, 분석 입력은 **시청자 녹화와 원본 콘텐츠 타임라인**이어야 한다.

### 장면별 질문에는 현재 요약만으로 근거가 부족함

1초별 집중·흥미 값은 내부에 있지만 전송 JSON에는 전체 시계열이 없다. AU 피크·미소 이벤트의 발생 시각도 없다. AU 평균·피크는 `face.aus_intensity`에서 집계하므로 개인 기준선 대비 AU 변화량으로 오인하지 않아야 한다.

시간은 영상 재생 위치가 아닌 세션 시작 후 경과시간이다. 전사문 `t`는 확정 전사를 세션에 기록한 시각이다. 재생 정지·탐색·STT 지연에 따라 영상 타임코드와 달라질 수 있다.

수정 요구: 콘텐츠·녹화 ID, 참여자 ID, `media_time_sec`, 구간별 유효성, 1초별 지표, 시각이 있는 이벤트, 원본/보정 AU 구분을 결과 계약에 넣는다. 타임코드가 없는 기존 결과에는 정밀 장면 설명을 제공하지 않는다.

### 집중·흥미·몰입도는 별도 검증이 필요한 합성 지표

`affect_analyzer.cpp`의 집중·흥미·긴장·참여는 시선·얼굴 자세·AU·감정 점수 등을 조합한 수식이다. 예를 들어 참여 지표는 집중 45% + 흥미 35% + 양의 각성도 20%를 조합한다. 이 지표 계산은 마지막 4채널 융합 블록보다 앞에 있다. 따라서 모든 지표가 최종 음성·언어 융합 결과를 똑같이 반영한다고 설명하지 않는다.

이번 시험은 수식 동작을 확인했으며 인간의 집중·몰입 측정 타당성을 확인하지 않았다. 판매 문구에는 관측 신호 기반 추정 지표임을 밝히고, 실제 콘텐츠 테스트와 비교 평가 후 표현을 확정한다.

### 제품용 작업·권한·삭제 기능은 별도 구현 대상

활성 집계 세션은 1개다. 재시작 시 기존 자료를 버리고 `finish()` 후 재조회할 저장 결과가 없다. 이는 여러 고객·참여자의 작업 관리 API와 다르다. `main.cpp`의 기존 API에서 고객별 OAuth 권한·A2A·구매 권한·보관 만료 처리의 구현은 확인하지 못했다. 다른 외부 시스템에서 제공되는지는 미확인이다.

수정 요구: 분석 작업 ID, 고객별 결과 권한, 반복 요청의 중복 방지, 처리 상태, 결과 저장·조회, 원본·전사·파생 결과·로그의 삭제 정책을 추가한다. 현재 세션 API를 그대로 인터넷에 공개하는 안은 채택하지 않는다.

## Marketplace 요건 검증

2026-10-23 공식 문서를 열어 확인했다. 실제 회사 계정의 가입·권한·심사 상태는 확인하지 않았다.

| 항목 | 확인 내용과 판단 |
| --- | --- |
| 판매 경로 | GE에서 사용하는 AI Agent as a Service는 A2A·Agent Card 및 Producer Portal 절차 필요 |
| 모델 기본 구성 | Google 기반 모델 또는 Model Garden 호스팅 모델 사용 조건. 해석 계층은 Gemini 전환을 설계 후보로 유지 |
| 호스팅 | 완전 GCP형 외에 하이브리드형도 명시됨. 하이브리드는 핵심 제품이 GCP에서 실행되고 사용 증가 시 GCP 에이전트 소비가 가장 빠르게 증가해야 함 |
| 현재 구성과의 차이 | A2A JSON 초안은 서비스 구현이 아님. 핵심 분석을 전부 회사 서버에 남기고 얇은 GCP API만 두는 구성을 자동 적합으로 판단할 수 없음 |
| 판매 준비 | 파트너·판매자 계정·결제 프로필과 production-ready 제품 요구. 이번 로컬 검증만으로 공개 판매 조건 미충족 |
| Agent Card | JSON 파싱 가능. 도메인은 예시이며 테스트 생성·A/B·알림 등 미검증 기능을 선언. 실제 구현과 맞춰 수정 필요 |

권고 구성은 **GCP A2A 서비스 + 작업 상태 저장 + 별도 CPU 배치 분석 작업 + 결과 저장 + Gemini 해석**이다. Cloud Run Jobs는 HTTP 요청을 받는 서버가 아니라 작업 후 종료하는 실행 환경이므로, GE 요청을 받는 서비스와 분리한다. Cloud Run은 Linux x86_64 실행 파일을 요구하므로 Windows EXE를 그대로 배포할 수 없다.

하이브리드의 실제 적합성과 자체 얼굴·AU 모델의 허용 범위는 설계도를 가지고 Google에 확인할 사안으로 남긴다. 회사 모델을 모두 Model Garden으로 옮겨야 한다고 단정하지 않는다.

## 월 70달러 예산의 검증 수준

**실제 운영비와 월 처리 가능량은 아직 미검증이다.** 공개 단가로 계산 가능한 범위와 실제 처리시간을 구분했다.

아래는 Cloud Run Jobs의 공개 Iowa 기본 USD 단가(CPU $0.000018/vCPU초, 메모리 $0.000002/GiB초)를 사용한 계산 예시다. 서울 리전 견적이 아니다. 무료 할당·할인·세금은 반영하지 않았다.

가정: 작업당 2vCPU·4GiB를 실제 과금시간 600초 동안 사용. 작업당 계산은 `600 × (2 × 0.000018 + 4 × 0.000002) = $0.0264`다. EmoAI가 이 자원과 시간 안에 영상을 처리한다는 의미는 아니다.

| 월 녹화 분석 작업 수 | CPU·메모리 계산액 |
| --- | --- |
| 100 | $2.64 |
| 500 | $13.20 |
| 1,000 | $26.40 |

이 금액에는 STT·Gemini·A2A 서버·저장·전송·빌드·이미지 보관·로그·보안 기능·재시도 비용이 빠져 있다. 참여자 30명이면 콘텐츠 1편도 녹화 작업 30건으로 센다. STT의 CPU/GPU 요구량이 미확인이라 이 표를 전체 비용 상한이나 판매 가능량으로 사용하지 않는다.

예산 알림은 자동 지출 차단이 아니다. 일부 서비스용 spend cap 기능도 문서에 있으나 이 구성 전체에 적용 가능한지는 미확인이다. 작업별 자원·시간·동시성 제한과 신규 접수 제한을 별도로 설계한다. 이번에는 무료 티어를 이용한 실제 리소스 생성도 하지 않았다.

## 상용화 전 확인할 권리 자료

기존 코드는 OpenFace를 포함한다. OpenFace 공식 저장소는 상업 라이선스 문의와 학습 데이터 라이선스 준수를 별도로 안내한다. 회사가 이미 확보한 라이선스가 있는지는 이번에 확인하지 않았다. 사용한 모델·학습 데이터·수정 코드의 권리 자료를 확보해야 하며, 무료 다운로드를 상업 배포 허용으로 취급하지 않는다. 법적 적합성을 판정한 것은 아니다.

2. 분석 코어: UI·마이크 캡처·외부 LLM과 분리해 영상·파일 오디오 배치 처리.
3. 로컬 실행: 동의와 이용 범위를 확인한 시험 영상으로 AU·표정·STT·요약을 연결하고 처리시간·최대 메모리 측정.
4. Linux 실행: 컨테이너에서 같은 입력의 결과·성능 비교. 현재 환경에는 Linux 실행기가 없어 미수행.
5. 클라우드 실측: 기존 월 70달러 예산 안에서 별도 실행 시 비용·호스팅 적합성 검증. 이번 무비용 범위에서는 미수행.
6. 제품 검증: A2A·인증·구매 권한·고객 격리·삭제·질의응답을 통합한 뒤 등록 문구·Agent Card 확정.
